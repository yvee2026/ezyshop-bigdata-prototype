## Summary of bottlenecks and optimisations

All effects below were measured on the development laptop (M3 Pro, Docker VM 12 vCPU / 7.65 GiB shared with unrelated containers; host load average 6–9 during the benchmarks).

| # | Bottleneck / problem | Change | Measured effect | Evidence |
|---|---|---|---|---|
| 1 | Default `spark.sql.shuffle.partitions` = 200: every micro-batch runs 200 tiny tasks per stateful stage, each committing its own state-store file | Set to **6** for local runs (`SPARK_SHUFFLE_PARTITIONS`) | Live-aggregation capacity on 3 cores, same 200k-event backlog: **1,512 → 8,941 ev/s (5.9×)** | `tests/bench/results/shuffle_partitions_experiment.txt` |
| 2 | Unbounded micro-batches under backlog: JVM OOM-killed | `maxOffsetsPerTrigger` 1,000,000 → 200,000 (100,000 / 50,000 in benchmarks); driver heap 2 g → 1.5 g; RocksDB bounded memory 256 MB | 1- and 3-core runs stable; 6 cores still OOM-killed in the full pipeline on this VM | T12, `throughput_resource_samples*.csv` |
| 3 | Bronze writer: 6 Delta commits per micro-batch to object storage | Kept 3 partitions (bronze writes parallelise across Kafka partitions); larger batches under load amortise the commits | Bronze capacity **3,842 → 5,317 ev/s** for 1 → 3 cores (+38%): the pipeline's limiting stage | T05, T11, `throughput.csv` |
| 4 | Speed-layer plan scanned Kafka 5× per batch | Single-pass fact normalisation | Input rows per batch 20,055–24,595 → 5,990–6,007 (= produced); batch time unchanged (6.5–9.8 s → 5.1–9.2 s) | T05 |
| 5 | Log flood (`KafkaDataConsumer` warning, 421k lines per run) | log4j2 config: that logger at ERROR | Log size 373,233 lines → 0 such lines. Load-sweep, 1 core, 4,000 ev/s offered: processed 2,092 → 3,708 ev/s between the first and second runs (but that comparison also changed the batch cap, so the gain cannot be attributed to logging alone) | T12 |
| 6 | VADER UDF called Python for every row | Score only non-empty texts | No significant effect (1 core 12,117 → 11,948 ev/s; 6 cores 8,301 → 9,196 ev/s, within noise) | T13 |
| 7 | Small files from streaming | Nightly `OPTIMIZE` (+ `ZORDER BY category` on silver) | Files 72 → 1 (bronze/clicks), 114 → 19 (silver/order_items); probe-query speed-up not distinguishable from warm-up at this size | T08 |
| 8 | Trigger interval | 30 s in production settings (A2: 1-minute windows instead of 10-second ones to save compute) | p50 freshness of the newest event 6.6 s (normal) / 9.0 s (burst); p95 average-event latency 27.8 s / 38.1 s, i.e. ~8–11× headroom against the 5-minute target | `latency_summary.csv` |
| 9 | Adding cores on one laptop | Measured 1 / 3 / 6 cores with a pre-loaded backlog | Live aggregation alone gets slower with more cores (12,388 / 9,545 / 7,774 ev/s): total task time 21 s → 122 s for the same work, JVM CPU only 6.9 s → 18.5 s, so tasks wait on Python UDF workers, state commits and a busy shared host. Scaling evidence therefore comes from the bronze stage (row 3) and is extrapolated with that caveat | T11 |

**What limited throughput:** in the full speed layer, the bronze Delta writer (object-store commits) at about 1,800–3,800 ev/s per core; then memory, since the 7.65 GiB VM, shared with other containers, cannot hold 6 Spark task slots with their Python workers. The live aggregation (about 9–12k ev/s) and Kafka (one Python producer sustained 50,000 ev/s) were never the limit.
